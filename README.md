# Shvft2.0 website

Static multi-page site for www.shvft20.org. No build step: each page is an `index.html` in its own folder (`about/`, `services/`, `how-we-work/`, `training/`, `for-businesses/`, `contact/`, `governance/`), sharing `styles.css`, `site.js` and `assets/`. Our impact and resources live on the home page; `impact/` only forwards old links to `/#impact`. The header and footer are repeated in every page, so change them in all of them.

Links use root paths (`/about/`), so preview with a local server rather than opening the file:

    python3 -m http.server 8000

## Bid readiness check

The free bid readiness check sits on the home page (`#readiness`), and `readiness/report/` shows the full report from the private link we email. `readiness/` only forwards old links to `/#readiness`.

- `readiness/framework.js` holds the questions, weights, essential (pass or fail) items, capacity flags and scoring, shared by both pages. It is built from the research report "Charity and CIC bid readiness" (October 2026), kept outside this repo in `Shvft 2.0/reports/`. Change `VERSION` whenever a question or weight changes, and review the questions each October.
- Submissions go to the `shvft-readiness-submit` Supabase function (in the Refuse the Box project) and are stored in `public.shvft_readiness_submissions`, with the exact permission wording each person agreed to. The function source lives in `Shvft 2.0/supabase/functions/`.
- Emails need the `SHVFT_SENDER_EMAIL` secret set to a Brevo-verified shvft20.org address; until then submissions are saved but not emailed.

## Consortium Portal

`portal/` is the signed-in system for the partners in each consortium Shvft2.0 manages (linked as "Partner sign in" in every footer, and kept out of search engines). It is a small app with no build step: `app.js` handles sign-in, two-step verification and routing, `lib.js` the shared helpers, and each screen is a file in `views/`.

- Data lives in its own Supabase project, "Shvft2.0 Consortium Portal" (London region), never alongside another business's data, with a staging copy for testing changes. The database, its access rules, edge functions and tests are in the private repository `T360impact/consortium-portal-db` (its README explains rebuilding, testing and deploying). `config.js` holds the public key; what anyone can see is enforced by row level security in the database, not by the pages.
- Roles: platform administrator, consortium lead, accountable body, delivery partner manager, hub or session worker, funder observer, youth voice and associate, plus extra roles (org admin, finance, safeguarding, ...). Platform administrators, leads, accountable bodies, partner managers and hub workers must use two-step sign-in, and the database refuses their password-only sessions. Funder and youth voice views are aggregates.
- **No records about individual young people.** The portal holds no young person's name, date of birth, contact details or full postcode. Each partner (or T360, for partners using it) uploads a weekly register summary: totals per site, programme and week on the fixed template `T360-WRS-1` (`views/uploads.js`). A file with names, dates of birth, contact details or full postcodes is turned away in the browser and again by the database, and nothing from it is kept. Confirmed weeks feed targets and the dashboard through `target_mappings`; returns are submitted and reviewed through `submit_return()` and `review_return()`; the dashboard comes from `consortium_progress()`. Free text everywhere is checked for the same identifying details.
- Invitations and reset links come from the `portal-admin` edge function (in `consortium-portal-db`), which emails them, or returns a one-time link to pass on until email is set up.
- Bids: a bid workspace is a consortium at the `bid` stage, so invited partners only ever see that bid. `views/bid.js` holds the checklist, uploads (every version kept), review with standard return comments, and the readiness view; partners see their own items and the overall percentage only. `convert_bid()` turns a won bid into the live consortium; `close_bid()` marks it not won. Checklist templates and the partner library (approved documents with an expiry date, reused by `apply_bid_template()` until they lapse) are in `views/library.js`, for Shvft2.0 staff only. Reminders show on each person's home screen for items due within a week or overdue; email reminders need a portal email sender first.
- Targets and budget (`views/targets.js`): the lead uploads programme documents (PDF, Word or Excel, every upload versioned) and runs the `extract-programme-data` function, which reads them with the Claude API and saves each target and budget line with its source passage; quotes that aren't in the document are flagged. The lead reviews each item, and `confirm_extraction()` stays blocked until `intake_review()`'s checks pass (partner targets add up, targeted share meets the minimum, budget equals the grant, nothing unallocated). Changes create new versions (`superseded_by`), nothing is deleted, and only partners whose figures changed confirm again with `confirm_partner_allocation()`. A bid can't be `mark_bid_submitted()` until every partner has confirmed. The function needs an `ANTHROPIC_API_KEY` secret in the portal project.
- Extraction reads documents as written: each line keeps the document's own wording, figure and unit, its section (e.g. Universal or Targeted), whether it's an output or an outcome, its priority and evidence text, and whether it's a yearly or a project-lifetime target (lifetime targets have no year). Outputs and outcomes link to organisations only where the document names them (`named_organisations`); the lead can tick others in review. Links live in `commitment_organisations` and drive the dashboard's "Outputs and outcomes by organisation" chart. Whether the targeted-share minimum applies every year or on average is set per consortium (`targeted_share_basis`).
- The budget is shown the way the budget document lays it out (`views/budget.js`): a project total, then one table per organisation with the document's cost categories in its order (`consortia.budget_categories`, zero rows included), its headings (`budget_sections`, e.g. "Lead Organisation", "Paid Delivery Partner 1") and its commentary on each category (`budget_notes`), then the funding breakdown with its limits (`funding_elements`, `funding_amounts`). These are loaded straight from the document's cells, not by the AI reading.
- Progress (`views/progress.js`): progress against the targets from confirmed weekly uploads and approved returns, with charts. Monthly figures that aren't in the weekly uploads are entered in each month's return; the page also offers that month's spreadsheet to download, fill in and upload (read in the browser with SheetJS; the file is kept).
- Summary (`views/hub.js`): what the partnership is for, who does what, what it measures, delivery, youth voice, governance, key dates and documents. It never shows money, for any role: `consortium_summary()` builds its answer field by field and only links documents that can't carry money (not budgets, grant agreements, the submitted bid or partner schedules). The lead edits a draft (`workspace_summary`, `organisation_roles_in_workspace`), can fill it from what the bid holds (`prefill_summary()`), and publishes it (`publish_summary()`, every version kept in `workspace_summary_versions`). The lead's edit view also holds the workspace records (organisations, sites, key dates, outcomes, details); the grant value is set under Targets and budget. Tests: `Shvft 2.0/supabase/tests/portal_summary.sql`.
- Portal design: every colour, space, radius and type size is a token at the top of `portal.css`, with a dark set (system setting, or `data-theme` on the root). Brand teal, an amber highlight, and an accent per module (bids, delivery, finance, surveys, evidence, compliance, governance) for icons, card top borders and chart series. Status text on its tint uses a darker shade than the status colour so every pill passes WCAG AA. Icons come from Lucide, inlined in `icons.js` with one fixed vocabulary (regenerate from `lucide-static`, don't hand-edit). Charts (`charts.js`) are plain SVG and HTML: rings, a donut with a minimum marker, bars with a "due by now" tick, stacked status bars and a line chart, each under a one-line takeaway. Desktop has a sidebar; phones get a bottom tab bar, 48px tap targets and cards instead of tables (`table.cards` with `data-label`).
- People can hold extra roles (org admin, finance, operations, reporting, safeguarding, bid contributor, hub worker) in `membership_roles`, on top of their main role. Budgets are visible to the lead, the accountable body, and a partner's own org admin and finance people.
- Tests: the database's access tests live in `consortium-portal-db/supabase/tests/sql/` and run in CI on every push to either repository, against a database rebuilt from the migrations. The portal's own tests (`portal/tests/`, `node --test 'portal/tests/*.test.mjs'`) cover navigation and the Content Security Policy; `npm run check` also runs ESLint and the type check.
- Demo workspaces (`consortia.is_demo`) hold made-up figures for practice and are labelled as such. The older `allow_real_records` flag gated the young person register, which no longer exists; it is no longer shown anywhere and the database still carries it only for history.
- Security: the portal page has a Content Security Policy (scripts only from this site; data only to the portal's Supabase project). Third-party libraries are served from `portal/vendor/` with recorded checksums, not from CDNs.
- Deploying: pushing to `main` runs every check and publishes to the staging site (https://staging.shvft20.org, its own Supabase project). The live site changes only when someone runs *Promote to production* in GitHub Actions for a commit that reached staging.

## Design and accessibility

- Icons live in `assets/icons.svg` (line icons in currentColor). Use `<svg><use href="/assets/icons.svg#i-name"/></svg>` inside `<span class="ico g|p|o">`.
- The brand gradient is kept for headline accent words (`.grad-text`) and the "2.0" in the wordmark only.
- Easy read (the "Aa" button in every header) switches to Atkinson Hyperlegible, larger text, more spacing and no motion (same page colours). A line in each page's `<head>` applies the saved choice before first paint; keep it when adding pages.
- Keep sentences short (aim for under 15 words) and use lists rather than long paragraphs.
- Partner logos live in `assets/partners/`; the strip scrolls sideways with a Pause button and stays still for reduced motion and Easy read.
